# 植物大战僵尸 —— C 语言复刻版

纯 C（C99）实现，**零第三方依赖**（不用 EasyX / SDL / raylib）。
渲染采用 2× 超采样后降采样抗锯齿；美术资源为 32 位带 alpha 的位图（预乘），
经 `AlphaBlend` 合成。

**同一份 `pvz.c` 同时构建两个平台**：

| 平台 | 状态 | 说明 |
|---|---|---|
| **Windows 桌面版** | 可玩 | Win32 GDI 绘制 + Direct3D9 呈现（初始化失败自动回退纯 GDI）。`pvz.exe` 已编译好，**双击即可开玩** |
| **网页版（iPad / 浏览器）** | 已构建通过 | 编译成 WebAssembly，[见下](#网页版webassembly--ipad)。为 iPad 做了触摸、横竖屏与安全区适配 |

> 另有一份 iOS 移植方案（[IOS_PORT.md](IOS_PORT.md)）已做到接口层，暂缓。

## 玩法

草坪 9×5，波数**因关卡而异**（前院/墓园 20 波、泳池 22 波、天台 24 波、沙漠 26 波、无尽 999 波），
**第 10 波与最后一波**是数量放大的「旗标波」。
任意一行的小推车用尽后还有僵尸走到最左边 → 失败；扛过全部波次 → 胜利。

| 操作 | 说明 |
| --- | --- |
| 左键点卡片 | 选中植物（阳光不足或冷却中无法选中） |
| 左键点草坪 | 种植到该格 |
| 左键点阳光 | 立刻拾取（默认会自动拾取，手动点更快） |
| `Esc` | 战斗/三选一中弹出暂停菜单，可选「继续游戏」或「回到主页」 |
| 右键 | 取消当前选择 |
| `1` ~ `9` | 快捷键选卡（按**卡槽位**，不是按植物种类） |
| `A` | **切换自动拾取阳光**（默认开） |
| `W` | **切换飘落特效**（默认开） |
| `S` | 抽卡界面里**跳过奖励**换取 +75 阳光 |
| `M` | 战斗中：**切换种植模式**（已解锁的模式之间循环）<br>元界面：**返回主菜单** |
| `G` | 消耗 10 金气，在鼠标格召唤一个南瓜炸弹 |
| `H` | 消耗 20 幽能，全屏僵尸减速 6 秒 |
| `F` | **合成植物**：把鼠标格与右邻格的植物融成混种 |
| `E` | 攒满愤怒条且持有「愤怒」遗物时，**主动引爆全屏雷击** |
| `Esc` / 右键 | 元界面返回主菜单 |
| **`F11`** / `Alt+Enter` | **切换全屏** |
| `P` / `空格` | 暂停 / 继续 |
| `R` | 重新开始 |

**自动拾取阳光**：阳光出现约 0.45 秒后自动飞向计数器，不需要手动点。
想自己收集就按 `A` 关掉，HUD 左下角会显示当前状态。

**开局阳光随关卡而异**（前院 150 / 泳池 175 / 墓园 200 / 天台 150 / 沙漠 225 / 无尽 200），
再叠加天赋与遗物加成；天空每 6~10 秒掉一颗阳光，向日葵每 17~23 秒产一颗。
普通植物与奖励植物的实际种植价格统一控制在 **50~500**：波次奖励植物首次落地免费，
以后重复种植按品质收费，卡槽会显示“赠”或真实价格。

## 肉鸽系统（每局都不一样）

**每波结束**弹出全屏三选一。卡池会提供新的奖励植物，以及可以重复叠加的成长卡：
第 1~10 波保证 **2 张植物 + 1 张成长卡**，第 11 波起固定为 **1 张植物 + 2 张成长卡**。
植物槽已满也不会改变卡面配比；此时选择植物会按品质折算为阳光补偿。
成长方向包括伤害、攻速、生命、爆炸、减速、冷却和穿透，单项最多叠 12 层。

**核心设计原则：随机只发生在「选择点」，绝不在「结算点」。**
拿到什么遗物是随机的；一旦拿到，效果 100% 确定。
绝不引入「一定概率打不中」这类随机——那会让玩家觉得「输赢不全由我决定」，
是最伤重玩心态的设计。

遗物按「改变数值 ↔ 改变玩法」分四类：

| 类型 | 例子 | 作用 |
| --- | --- | --- |
| **构筑定义型** | 同列共鸣（同列 ≥3 株 → 该列伤害 +25%）<br>留白（每个空位使相邻植物 +7%） | 决定这一局的打法，最好玩 |
| **数量堆叠型** | 花海（每株向日葵使植物生命 +6%）<br>坚果教条（每株坚果墙使射手伤害 +9%） | 靠布局投入换收益 |
| **风险改写型** | 背水一战（移除全部小推车，伤害 +65%）<br>玻璃大炮（伤害 +80%，生命 -45%） | 改变风险结构，制造真正的取舍 |
| **基础填充型** | 豌豆伤害 +12%、卡片冷却 -8% | 保证池子有梯度 |

**「跳过」很关键**：每次三选一都可以放弃，换 75 阳光。
没有跳过，三选一就只是三选一；有了跳过，玩家才会真正权衡「这一张值不值得拿」。

**难度必须同步调陡**——遗物成长会让原来的线性曲线被完全碾平：

```c
budget = 2 + idx;                                        /* 第一版：第 20 波 = 22，肉鸽下毫无压力 */
budget = 2 + idx*1.4 + idx*idx*0.085;                    /* 第二版：第 20 波 = 59，实测仍然太松 */
budget = 2 + idx*1.9 + idx*idx*0.95 + idx*idx*idx*0.030; /* 现版：第 20 波 = 660 → 旗标 x1.55 = 1023 */
```

### 架构：数值抽象层

加遗物最大的工程风险是「改一处漏三处」——原来代码里费用、伤害、血量、速度全是写死的常数，
散落在十几处。所以先做了一层取值函数：

```c
static int   plantCost(int t);      /* 基础 → 遗物修正 → 向日葵专修 */
static float plantCd(int t);
static float plantHpMax(int t);
static float peaBaseDmg(void);
static float shootGap(void);
static float zombieHpMax(int t);
static float slowDur(void);
static float fieldDmgBonusAt(int row, int col);   /* 依赖棋盘布局的加成 */
```

修正分两层：
- **全局修正量**由 `relicsRecalc()` 在获得遗物时统一重算（乘数/加数）
- **棋盘相关加成**（同列共鸣、留白、坚果教条、温床、尖兵、纵深防御）在开火那一刻按当前布局算，
  不能用全局预计算——它们每时每刻都在变

之后每加一个遗物只需要在一个地方挂钩子。

### 四个"改玩法"的系统

普通遗物是「这一局变强」，下面四套是「这一局变成另一种游戏」：

| 系统 | 内容 | 怎么改变玩法 |
| --- | --- | --- |
| **6 种种植模式** | 标准 / 双株 / 多列 / 水中 / 夜间 / 塔防 | 决定这一局的布局逻辑：双株同格叠两株、多列一株占 2 列、水中只能种后 3 列、夜间换暗色草坪、塔防一株占 2 行高 |
| **5 种武器模组** | 穿透 / 溅射 / 反弹 / 冰冻 / 灼烧 | 射手的主射和副射**交替开火**，两种武器混搭 |
| **3 种货币** | 阳光 / 金气（击杀获得）/ 幽能（减速获得） | 三条资源线要同时平衡 |
| **2 套能量** | 愤怒条（45 秒满，全屏雷击）/ 充能槽（下次爆炸 +60%） | 决定先手还是攒着 |

模式用 `M` 键切换，货币用 `G` / `H` 花掉。

### 窗口与全屏

游戏使用 **1000×650** 逻辑坐标与 **2000×1300** 高分辨率世界层，窗口尺寸任意时做**等比缩放 + 黑边**（不变形）：
- `F11` 或 `Alt+Enter` 切换全屏
- 用**无边框窗口铺满显示器**，而不是 `ChangeDisplaySettings` 真全屏 ——
  后者会改用户的显示分辨率，切出去还要黑屏恢复
- 高 DPI / 全屏输出直接从 2× 世界层一次采样到显示器，不再先降到 1000×650 后二次放大
- 鼠标坐标会**反向映射**回游戏坐标系（`windowToGame()`），
  所以全屏/缩放下点击依然精准

### 难度（第三版）

| 版本 | 曲线 | 真人实测 |
| --- | --- | --- |
| v1 | `2 + idx`（线性） | 100% 通关，太松 |
| v2 | 加平方项 | 仍然太松 |
| **v3** | **移除羁绊 + 线性/平方/立方三项 + 出怪密度压缩** | 目标 5% |

v3 的四个杠杆：
1. **移除羁绊系统** —— 它白送了约 25% 强度（射手 3 档 -28% 射击间隔最明显）
2. **难度曲线加立方项**：`2 + idx*1.9 + idx²*0.95 + idx³*0.030`
3. **僵尸血量 +30%、速度 +12%**
4. **出怪密度压缩**：同一波内散布窗口 10 秒 → 3.5 秒；波间隔 23 秒 → 17 秒

> 第 4 条才是关键：波次预算早就超过出怪上限（160 只），
> 继续堆预算没用，**"同样数量的僵尸在更短时间内涌出"才是真正的难度杠杆**。

### 三选一：必有且仅有一张植物卡

**每次三选一，三个选项里必定有且仅有 1 张植物卡**（概率 100%），另外 2 张是遗物。
植物卡按以下顺序取内容，所以永远不会出现「三个全是遗物」：

| 优先级 | 内容 | 生效范围 |
| --- | --- | --- |
| ① | 本局还没拿到的**神级植物**（按稀有度权重抽） | 只在本局生效，占一个额外卡槽 |
| ② | 神级卡槽满（6 个）或 8 株都拿过 → **永久解锁一株普通植物** | 写进存档，编组/抽卡池都能用 |
| ③ | 连普通植物也全解锁 → **植物精华**（阳光 +250、金气 +25） | 兜底，不会退回「全是遗物」 |

> ②③ 是为了让「100% 有植物卡」在后期依然成立。
> ① 是每局随机的一部分，跨局不带（旧版写进存档是 bug，已修）。

### 抽卡 → 编组 → 出战 的闭环

```
打完一局 → 结算抽卡（三张盲盒选一张翻开）→ 解锁一株新植物（自动加入编组）
                                              ↓
大厅「编组」→ 在 32 株里点选 5 株候选 → 存档记下 → 下一局顶部只出其中前 4 张卡
```

**为什么卡槽要卡死很重要**：普通植物有 32 种，候选池最多 5 株、实战只带前 4 张，
所以"抽到新植物"不是简单的进度条增长，而是**「我要不要换掉现在这套」的取舍**。
编组选择会存进 `pvz_save.dat`，下次打开还留着。

**每局结束的抽卡是免费且必给的**（不看胜负），保证每局都有产出——
这是让玩家愿意开下一局的关键。

### 神级植物（三选一里的植物卡）

三选一抽卡里会**按概率混入"植物卡"**——选中就解锁一株神级植物，
并**在本局额外占一个卡槽**（不挤掉原有 4 张编组）。

| **稀有** | 55% | 烈焰射手 | 三行火焰弹，穿透 2 个目标并留火 | 58 vs 豌豆 24 = **2.4×** |

| **史诗** | 28% | 晶簇射手 | 上下三行齐射，每发 55 | 55 vs 三线 18 = **3.1×** |
| | | 荆棘藤蔓 | 覆盖整行 9 格，每秒 130 | 130 vs 地刺 45 = **2.9×** |
| **传奇** | 13% | 太阳神花 | 每次 180 阳光，每 8 秒治疗全部植物 400 | 180 vs 25 = **7.2×** |
| | | 霜之哀伤 | 每 4.5 秒冻结全屏僵尸 3 秒 | 全屏控制 |

## 美术资源

完整的美术规范见 **ART_BIBLE.md**。

| 类别 | 文件 |
| --- | --- |
| 植物 ×8 | `sunflower` `peashooter` `wallnut` `potatomine` `snowpea` `repeater` `cherrybomb` `jalapeno` |
| 僵尸行走 ×4 | `zombie_normal` `zombie_cone` `zombie_bucket` `zombie_flag` |

### 草坪是怎么做的

草坪不是一张贴图，是**离线合成的八层**（运行时零开销，一张图直接画）：

| 层 | 内容 |
| --- | --- |
| L1 | 细草底纹（镜像平铺 2×2，天然无缝，比拉伸更像草地） |
| L2 | 大尺度色斑（低频噪声，打散平铺的规律感） |
| L3 | 斜向割草条纹（很淡，暗示修剪过的草坪） |
| L4 | 9×5 棋盘格（明度差 9%，给玩家格子感） |
| L5 | **方向光**：左上偏暖提亮、右下偏冷压暗 |
| L5.5 | 树影斑驳（10 块柔和明暗斑） |
| L6 | 随机贴花（草簇/小花/石子，随机旋转缩放，边缘更密） |
| L7 | **边界收口**：最外圈土色边 + 内侧一圈受光更亮的浅色草边 + 沿线点缀鹅卵石 |
| L8 | 暗角 + 左侧房屋方向的投影 |
| L9 | 调色（提饱和/提亮/提对比） |

**为什么要有 L5 方向光**：角色资源是「左上暖主光 + 右下冷轮廓光」画出来的，
草坪如果整体均匀，看起来就像和角色是两个图层拼在一起的。加上同方向的光照梯度后才有整体感。

**回退机制**：启动时逐张尝试加载，任何一张缺失，对应对象就自动退回程序化绘制。
**把 `assets/` 整个删掉，游戏照样能跑**（只是画面变回几何图形风格），也方便逐个替换做 A/B 对比。

### 僵尸倒地动画：不用生成，旋转派生

僵尸死亡不再是「直接变粒子」，而是先播 0.42 秒倒地动画。**5 帧全部由行走姿态
绕「脚底」旋转离线派生的**（`make_fall_frames`）：

- 零生成成本，且与行走姿态**完全同源** —— 配色画风绝对一致
- 绕脚底而不是绕中心旋转，倒下时脚是不动的，符合物理直觉
- 每帧裁剪后把脚底重新对到底边中点，所以 5 帧共用同一个锚点，代码里直接换图即可
- 末段 32% 时间淡出，衔接粒子爆散

**结论：不是所有动画都需要生成。能用几何变换从已有素材派生的，派生比生成更好**
（一致、免费、可控）。

### 天气层（飘落花瓣）

44 个花瓣/枯叶从顶部飘落，左右摇摆。GDI 画不了旋转图元，
所以用**椭圆宽度振荡**伪造翻转——正面是宽椭圆、侧面是细长条，看起来就在打旋。

> 注意别把公式写反：`rx` 随 `|cos|` 收窄、`ry` 基本不变，
> 才是「一张平面的花瓣在自转」；反过来会变成一个时胖时瘦的圆点，像噪点。

画在僵尸之后（花瓣从近处飘过）、阳光之前（不遮挡可点击的阳光）。`W` 键开关。

### 重新生成美术资源

```bash
cd art
python build_assets.py          # 读 raw/*.png -> 抠图 -> 合成 -> 输出 ../assets/*.bmp
```

生成器的坑（脚本里都处理了，细节见 `art/build_assets.py` 注释）：

1. 所谓「透明背景」其实是**把棋盘格画成了像素**，必须自己抠
2. 不同图的背景不统一：多数是浅色棋盘格，个别是**纯黑**
3. 主体周围有一圈**柔光晕**，要「腐蚀核心区 + 边缘软键」才能去掉
4. 僵尸两腿之间的**封闭背景口袋**泛洪抓不到，会变成白块贴在角色上
5. **Pillow 12.3.0 的 `ImageDraw.floodfill` 在 `'L'` 模式下是坏的**（实测：100×100 全白图填充后毫无变化），
   所以自己写了扫描线连通域填充
6. 图生图改姿势时，**角色一致性优先于姿态幅度**——
   给参考图 + 姿态提示能保住角色设计（衣服/脸/画风），动作幅度偏保守；
   不给参考图动作幅度够大但角色会变成另一只僵尸。一局游戏里同一只僵尸不能一啃食就换衣服。

## 网页版（WebAssembly / iPad）

同一份 `pvz.c` 同时构建桌面版与网页版。网页版可在 iPad Safari 里直接玩，
建议**添加到主屏幕**后从主屏幕启动（全屏，没有地址栏）。

完整方案与验证记录见 **[WEB_PORT.md](WEB_PORT.md)**。

### 架构

```
                  ┌─────────────────┐
                  │     pvz.c       │  游戏逻辑（约 14,000 行）
                  │  零平台依赖      │
                  └────────┬────────┘
                           │ 只通过 plat.h 的接口访问平台
         ┌─────────────────┼─────────────────┐
         ▼                 ▼                 ▼
   ┌───────────┐    ┌────────────┐    ┌───────────┐
   │  直通      │    │ plat_web.c │    │ (预留)     │
   │  GDI/D3D9 │    │  软件光栅   │    │ iOS       │
   │  Windows  │    │ WASM / 本机 │    │           │
   └───────────┘    └────────────┘    └───────────┘
```

`plat.h` 在 Windows 下是**直通**（只 include windows.h，不包一层），
所以桌面版行为一个字节不变；可移植侧实现同一批符号。

| 项 | 实测值 |
|---|---|
| 游戏逻辑（零平台依赖） | 约 13,600 行 |
| 平台代码（WinMain + 窗口/输入/音频/呈现） | 约 650 行 |
| 需要重写的绘制原语 | **22 个** |
| 需要实现的 Win32 符号 | **56 个** |
| `plat_web.c` | 约 1,600 行 |

两个让移植变简单的实测结论：
1. `CreateFontW` **全工程只有 1 个调用点** → 文字渲染只需换一个入口
2. MCI 只用了 **6 个动词**（open/play/stop/pause/close/status）→ 直译 Web Audio

### 渲染路线：软件光栅 + 每帧一次上传

不是"每个原语调 Canvas2D"——每帧有数百到上千次绘制调用，逐次跨 JS 边界开销太大，
且 GDI 语义（预乘 alpha、世界变换、剪切区）要逐个映射、容易出静默偏差。

```
游戏逻辑 ──> 世界层 2000×1300 (BGRA) ──> BGRA→RGBA + alpha=255 ──> canvas
              （逻辑 1000×650 × SS 2）        （外壳里做）
```

选软件光栅还有个**决定性优势**：它是纯 C，**本机 gcc 就能编译 + 逐像素验证**，
不必等 WebAssembly 工具链。移植期 90% 的风险都靠这条查出来。

> 世界层故意**不写 alpha**（GDI 的填充图元就是只写 RGB），
> 这样它的字节流与 Windows 版**逐字节可比**（抓帧基线会 dump 全部 4 字节）。
> canvas 需要的 alpha 由外壳补 —— 转换放在外壳，不放在光栅后端。

### iPad 适配

游戏内部坐标恒为 **1000×650**，适配全在呈现层：

| 项 | 做法 |
|---|---|
| 分辨率 | canvas 像素尺寸恒为 2000×1300；显示尺寸按"等比铺满 + 居中"算。iPad 各型号（1180×820 / 1194×834 / 1366×1024）都不用改引擎 |
| 裁切 | 用 **contain 而非 cover** —— cover 会把草坪两侧切掉，而草坪边缘正是"僵尸从哪来"的信息 |
| 触摸 | 点按=确认；**长按 250ms=悬停**（触摸没有 hover，必须给替代）；拖动=种植手势，且不误触为点击 |
| 命中区 | 可点元素不小于 **44×44 pt**（Apple HIG 下限） |
| 方向 | 横屏是主力形态；竖屏给一个**可关闭**的提示但**仍可玩**。监听 `resize` / `orientationchange` / `screen.orientation` 三条路径（iPad 上不同 iOS 版本触发的组合不同），切换后重算触摸映射 |
| 安全区 | `viewport-fit=cover` + `env(safe-area-inset-*)` |
| 键盘 | iPad 没键盘 → 左下角一排屏幕按钮，走**同一个** `handleKey()`（所以行为不可能和桌面分叉） |
| 音频 | iOS 要求**用户手势**后才能出声 → 启动页的"点击开始"按钮同时承担解锁 `AudioContext` 的职责 |
| 后台 | iOS 会随时冻结页面 → `visibilitychange` 时立刻存档并暂停；`pagehide` 比 `unload` 可靠 |

### 音频分工（刻意的）

| 类型 | 体积 | 走法 |
|---|---|---|
| 音效 `sfx/*.wav` | 1.3 MB | MEMFS + Web Audio，低延迟 |
| BGM `bgm/*.mp3` | 20 MB | HTMLAudio 按 URL **流式**播放 |

BGM 不塞进 MEMFS：20MB 常驻内存不划算，而 HTMLAudio 支持边下边播，
进游戏不用等整首下完。

| − `art/` 下的素材生产中间产物 | |
| **实际入库** | **约 82 MB / 1158 文件** |

### 网页版踩过的坑

都是**不报错、只是画错**的类型，靠逐像素比对与端到端测试才抓到：

| # | 坑 | 症状 |
|---|---|---|
| 1 | `FillRect` 取色读到对象池的 `type` 字段 | 所有填充变成 R=2 的近黑，整屏几乎全黑 |
| 2 | 以为 `AlphaBlend` 不吃世界变换（见上文修正） | 缩放类绘制整体差 2 倍 |
| 3 | `Polygon` 内外判定用了**未变换**的坐标 | 只画出应画面积的 40%（位置对、范围不对） |
| 4 | `putOpaque` 写了 alpha | 每个原语都报"100% 不同"，而 RGB 其实逐字节一致 |
| 5 | `plat.h` 里 `NULL_PEN` 与 `NULL_BRUSH` **都是 NULL** | 后端无法区分"只填充"与"只描边"（引擎里分别用了 4 处和 8 处） |
| 6 | 缺 `GdiFlush` | GDI 绘制是批处理的，不 flush 读 DIB 拿到陈旧内存 |
| 7 | `draftPickOne` 的边界 | `n<=0` 时 `rand()%m` 是**除零**；`n>R_COUNT` 会**越界写栈** |
| 8 | `_wfopen` 未转反斜杠 | MEMFS 与 POSIX 都不认反斜杠 → wasm 下素材**全部**加载失败。⚠️ 本机 Windows 的 `fopen` 恰好能吃反斜杠，**本地验证拦不住** |
| 9 | `[hidden]` 被 `display:flex` 覆盖 | 横屏时那个提示层不可见却**吃掉所有触摸**，游戏完全点不动。截图看一切正常 |
| 10 | `checkOrientation()` 里的 `if(!running) return` | 顺序依赖 → 竖屏提示永远不出现 |

## 编译

```bash
gcc -O2 -mwindows -static-libgcc -o pvz.exe pvz.c -lgdi32 -luser32 -lmsimg32 -lwinmm -ld3d9 -lm
```

或者直接双击 / 运行 `build.bat`（会自动查找 PATH 和 winget 安装的 MinGW）。

- `-lmsimg32` 必需 —— 精灵合成用 `AlphaBlend`
- `-ld3d9` 必需 —— 全屏缩放、黑边与垂直同步由 GPU 呈现；初始化失败会自动回退 GDI
- `-static-libgcc` 别省 —— 否则依赖 MinGW 的 `libgcc_s_dw2-1.dll`，换台没装 MinGW 的电脑就启动不了。
  加上后依赖只剩 `GDI32 / USER32 / KERNEL32 / MSIMG32 / msvcrt`，所有 Windows 都有。

## 代码结构（单文件 `pvz.c`，约 14,000 行）

| 区块 | 内容 |
| --- | --- |
| GDI 缓存层 | 画刷 / 画笔按 (颜色, 宽度) 缓存，避免每帧创建 GDI 对象 |
| 绘图小工具 | `fillCircle` / `fillEllipse` / `fillRect` / `fillRound` / `poly` / `putText*` |
| **精灵系统** | `spriteLoad`（`stb_image` 解码 PNG/JPEG/BMP → `CreateDIBSection`）、`spriteTint`（剪影）、`spriteBlit`（`AlphaBlend`） |
| 植物造型 | `drawPlantShape()` 有资源走精灵，无资源回退 `drawPlantShapeProc()`；同一函数复用于场景与卡片图标 |
| 僵尸造型 | `drawZombie()` / `drawZombieProc()`，同上双路径 |
| 游戏逻辑 | `updateGame()` 波次、出怪、植物技能、豌豆、僵尸、推车、阳光、粒子 |
| 输入 | `onClick()` 统一处理卡片 / 草坪 / 阳光点击 |
| 渲染 | `render()` 世界层与文字层统一按 2× 绘制 → 根据窗口尺寸一次采样输出 |
| 窗口 | `WndProc` + `WinMain`，固定窗口尺寸，60 FPS 限帧主循环 |

### 两个渲染坑

**1. 高分辨率合成**：所有图形与文字都在 `gWorldDC`（1000×650 逻辑坐标，
`SetWorldTransform` 放大 2 倍到 2000×1300 物理像素）绘制。普通窗口生成一份 1× 兼容帧；
高 DPI 或全屏输出直接从 2× 世界层一次采样到目标尺寸，避免先降到 1× 再放大导致模糊。

**2. 精灵坐标**：`spriteBlit` 会临时把变换复位、用 `逻辑坐标 × SS` 计算目标矩形，
画完再恢复。精灵始终画在世界层，由 `spriteBlit` 负责逻辑坐标与资源像素之间的换算。

> ⚠️ **上面这段里原来的说法「`AlphaBlend` 不受世界变换影响」是错的**，2026-09-21 实测推翻：
>
> GDI 在 `GM_ADVANCED` 下，`BitBlt` / `StretchBlt` / `AlphaBlend` **都会应用世界变换**。
> 实测依据：目标矩形传 32 设备像素，GDI 实际输出 64（正好 ×SS=2）。
>
> 之所以一直没暴露，是因为 `spriteBlit` 里**恰好**先 `SetWorldTransform(gIdentXF)`
> 复位成了单位变换 —— 此时"吃不吃变换"结果相同，两种理解**无法区分**。
> 直到写网页版的软件光栅后端、做了**独立的原语级 A/B 测试**
> （`_ab_prim.c`，同一个测试分别链接真 GDI 与软件光栅），才把这件事钉清楚。
>
> 教训：**"看起来对"不等于实现正确**。当代码里存在一个让两种相反理解等价的
> 巧合条件时，任何基于该路径的测试都无法证伪它们。

## 附：`sim_test.c`（无窗口对局模拟）

用来快速验证玩法与调平衡，不需要人工试玩。它直接 `#include "pvz.c"`，
以一个朴素的自动决策 AI 用固定步长把整局快进跑完，每隔 60 秒打印状态，
最后给出胜负、总时长、击杀数、剩余小推车。

```bash
gcc -O2 -o sim.exe sim_test.c -lgdi32 -luser32 -lmsimg32 -lm
./sim.exe
```

**调难度别只看一局**：实测同一份代码连跑 10 局可能是 5 胜 5 负。
建议至少跑 10 局看胜率再动手改数值。

一个实测结论：**僵尸啃食速度是难度的主导变量**，比调豌豆伤害有效得多。
啃食 90/秒时这个 AI 只有约 50% 胜率，而且输的局几乎都是**前期崩盘**
（向日葵被啃 → 阳光断供 → 恶性循环）；降到 80/秒后胜率约 85~92%。
真人手上有樱桃炸弹 / 火爆辣椒 / 土豆雷 / 坚果墙，会宽松不少。
