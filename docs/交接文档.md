## 一、项目速览

**纯 C + Win32/GDI 的植物大战僵尸类游戏**，单文件 `pvz.c`（约 1 万行），
无第三方依赖，编译产物 `pvz.exe` 双击即玩。

| 项目 | 说明 |
|---|---|
| 主源码 | `pvz.c`（单文件，所有逻辑都在里面） |
| 美术资源 | `assets/*.bmp`（引擎只读 32 位带 alpha 的 BMP） |
| 音频资源 | `assets/bgm/*.mp3`、`assets/sfx/*.wav` |
| 玩家存档 | `pvz_save.dat`（**不要动**，真实进度） |
| 设计文档 | `docs/新关卡设计方案.md`、`docs/美术与音乐素材清单.md` |
| 当前关卡数 | **11 关**（第 0~10 关） |
| 存档版本 | v5（1012 字节） |

**玩法结构**：主菜单 → 选关 → 战斗（波次 + 三选一肉鸽）→ 结算。
11 个关卡各有独立规则，第 6~10 关是最近新增的。

### 目录里什么能删、什么不能删

跑测试和生成素材会攒下大量中间产物。**已清理过一次（864M → 492M）**，
接手后请维持这个整洁度：

| 路径 | 大小 | 能否删 |
|---|---|---|
| `assets/` | 268M | ❌ **运行时资源**，删了游戏没图没声 |
| `art/raw/` | 123M | ⚠️ AI 生成源图（原始素材）。已被处理进 `assets/`，但**是重新处理（改抠图阈值/重新裁切）的唯一来源**，建议保留 |
| `_frames*/` | 每次跑测试 5~33M | ✅ **测试输出，随时可删**，重跑即有 |
| `assets_new/` | 8.4M | ⚠️ 第 6~10 关的成品素材（已入库到 `assets/`），可作备份保留 |
| `docs/` | 48K | ❌ 文档 |
| `*.exe` | 各 300K | ✅ 构建产物，可删（保留 `pvz.exe`） |
| `_dump.exe` | 315K | ✅ `_mk_framedump.py` 重新生成即可 |
| `pvz_save.dat` | 1K | ❌❌ **玩家真实进度** |
| `pvz_save.dat.bak-*` | 1K | ⚠️ 进度备份，建议保留 |
| `pvz.c.bak-*` | 各 500K | ✅ 源码快照，留最新一个即可 |

**定期清理命令**（安全，只删测试输出和构建产物）：

```bash
cd pvz-c
rm -rf _frames _frames_*          # 测试输出（每次跑验证脚本会重新生成）
rm -f _*_test.exe _hudtest.exe _uiaudit.exe _uiproof.exe   # 旧测试 exe
```

**不要**用 `rm -rf` 通配删 `assets/` 或 `art/raw/` —— 那是不可再生的。

### 无头测试（重要）

游戏是窗口程序，但项目有一套**可脚本化的测试方式**：

```bash
python _mk_framedump.py      # 生成 _dump.exe（注入调试热键 + 状态输出）
```

`_dump.exe` 会：
* 把内部状态写到环境变量 `PVZ_DUMPDIR` 指向的目录（`stat30.txt` 等）
* 支持一批调试热键（见下表）

然后用 Python 发 `PostMessage` 模拟按键/点击，读 `stat30.txt` 断言。
现成例子见 `_verify_levels.py`（结构清晰，可直接抄）。

### P0-1 · 第 9 关的「断电」机制没有实际效果

**现象**：短路僵尸切断整行供电后，只显示一条红色指示条，**该行植物照常攻击、照常产阳光**。
第 9 关的核心威胁是假的。

**根因**：`gPowerCutRow[]` 这个数组只被三处使用 ——
声明、每帧倒计时、绘制指示条。而**真正该做的「让植物停止工作」从未实现**。

我在注释里引用了 `newLevelRowPowered()`，但**这个函数在代码里根本不存在**：
```bash
grep -n "newLevelRowPowered" pvz.c    # 只有注释里提到，没有定义
```

**要改的地方**：

1. 搜索 `static float gPowerCutRow[ROWS]` → 这是断电倒计时数组
2. 搜索 `switch (p->type)` **在 `updateGame()` 里**（约 7242 行）→
   这是植物行为的逐帧分发，断电门应该加在这里，
   或者加在更靠上的"该植物本帧是否应该行动"的判定处
3. 推荐实现一个 `newLevelRowPowered(int row)` 返回 0/1，
   在植物行为分发前拦截：

```c
/* 关 9：该行是否通电。断电期间该行植物不工作。 */
static int newLevelRowPowered(int row)
{
    if (gRuleKind != RULE_POWER) return 1;      /* 其他关卡不受影响 */
    if (row < 0 || row >= ROWS) return 1;
    return gPowerCutRow[row] <= 0.0f;
}
```

**验收标准**：
* 断电期间该行所有植物停止攻击、向日葵停止产阳光
* 8 秒后自动恢复
* 其他关卡完全不受影响（回归 `_verify_levels.py`）
* 断电时植物的视觉状态应该能看出来（例如整体变暗）

**现状**：地形危害目前是**程序化色块绘制**（功能正常，但不如贴图精致）。

#### ⚠️ 关键：这批素材**没有 alpha 通道**，不能直接 blit

实测这批 BMP 的透明比全部是 **0.0%** —— 它们在入库时是当作不透明图缩放的：

| 资源 | 尺寸 | 角落背景色 | 接入前必须先处理 |
|---|---|---|---|
| `fx_ember` | 1728×972 | 纯黑 `[0,0,0]` | **抠黑** 或加法混合 |
| `fx_snowstorm` | 1728×972 | 纯黑 `[0,0,0]` | 同上 |
| `fx_fog` | 1728×972 | 近黑 `[16,1,5]` | 同上 |
| `hazard_thin_ice` | 192×192 | 深棕 `[70,45,1]` | 抠背景 |
| `hazard_rift` | 192×192 | 深色 `[25,12,14]` | 抠背景 |
| `node_power` | 192×192 | 深色 `[29,17,15]` | 抠背景 |
| `fx_meteor` | 192×192 | 深红 `[29,1,1]` | 抠背景 |

**直接 `AlphaBlend` 会把整块背景色糊到草坪上**，画面会明显变脏。

**两条可行路线（推荐 A）**：

**A. 先用 `_install_art.py` 重新入库成带 alpha 的版本**（推荐）
该脚本已有 `chroma_key()`（绿色背景抠图）和 `fillRectA` 之外的处理。
给黑色/深色背景的素材加一个"暗底抠图"模式即可：把接近背景色的像素 alpha 置 0，
边缘用软阈值过渡（硬切会留锯齿）。这是最省事、效果最稳的路子。

**B. 运行时用特殊混合模式**
GDI 的 `AlphaBlend` **只支持 `AC_SRC_OVER` 一种 BlendOp**，
没有真正的加法混合。变通做法是 `BitBlt` + `SRCPAINT`（按位或），
能近似模拟"发光叠加"，但对 `hazard_*` 这类需要精确遮挡的贴图不适用。

**其他注意点**：
* `hazard_*` 是 192×192，而一个格子在贴图空间是 **192×200**
  （`CELL_W=96, CELL_H=100`，草坪贴图 1728×1000 是 2 倍缩放）——
  接入时按格子尺寸缩放，否则会有缝
* 加载方式参考同文件已有资源：`spriteLoadName(&gSprXxx, L"名字")`，
  需要先声明 `static Sprite` 全局量

**要改的地方**：`drawTerrainOverlay()`（搜索该函数名）里的
「新五关的场地可视元素」段落 —— 把 `fillRectA(...)` 的色块换成贴图 blit。

**验收标准**：
* 五关截图里能看到贴图替代了色块
* **画面没有变暗、没有出现方块状色斑**（这是最容易翻车的地方，
  务必用截图目视确认，状态 dump 看不出这类问题）

## 五、⚠️ 必须遵守的约定（都是踩过的坑）

### 1. 存档结构体里**绝对不能用会变化的宏**

```c
#define LV_COUNT 11               /* 关卡数 */
typedef struct {
    int lvStars[LV_COUNT];        /* ✗✗✗ 危险！ */
    int lvUnlocked[LV_COUNT];     /* ✗✗✗ 危险！ */
} SaveData;
```

**为什么**：把 `LV_COUNT` 从 6 改成 11 的那一刻，整个存档布局就变了
（972 → 1012 字节），`saveLoad()` 的 `nread >= sizeof(SaveData)` 判定对老档失败，
**直接掉进 `saveResetNew()` 清空玩家进度，且没有任何报错**。
（本项目真实发生过：玩家 7 星 / 69 株植物被重置成 2 星 / 19 株。）

**正确做法**：写死常量
```c
#define SAVE_LV_V2V4  6           /* 那一版的关卡数，永不跟随 LV_COUNT */
```

改存档结构时**必须做三件事**：
1. `SAVE_VER` +1
2. 保留旧版结构体定义（数组长度写死），才能读出老进度
3. 写**逐字段**迁移分支（偏移全变了，不能整块 memcpy）

### 2. 测试脚本必须隔离存档

```python
env["PVZ_SAVE_FILE"] = os.path.join(D, "_test_save.dat")   # 副本！
```

**漏了这行的脚本跑一次就会改写玩家真档**，而且因为逻辑正确你不会发现。
（本项目有 3 个脚本踩过这个坑，现已修。）

### 3. UI 承诺的事必须真的能做到

底部提示曾写着「右键 / Esc 返回」，但 Esc 的分支只做了
`gSel = -1; gShovel = 0;` —— **根本不返回**。玩家按 Esc 没反应就以为卡死。
而且当时界面上**没有任何可见的返回按钮**，只有一行小字。

**根因是双路径各写一份**：右键能返回、Esc 不能，两处独立实现，
改一处必然漏另一处。现在三条路（按钮 / Esc / 右键）共用 `goBack()`。

教训：**改动导航/快捷键这类多入口功能时，一律收敛到一个函数**，
并在界面上给出**可见入口**（不能只靠提示文字教玩家按快捷键）。

### 4. 调试热键要镜像真实玩家路径

`V` 键曾漏掉 `bgmForLevel()`，导致"新关卡没有 BGM"看起来像 bug，
实际只是测试键没走完整流程 —— **会把你引到错误的排查方向**。
新增调试键时，对照 `onClick()` 里真实路径把该调的调用都补上。

### 5. 关卡规则优先做成「种植约束」或「场地事件」

不要去改植物/僵尸的行为逻辑 —— 伤害点有十几处，逐处嵌入既容易漏，
又把关卡规则和单位行为耦合死（加第 12 关就得再动一遍）。
现有规则都遵循这个原则，请延续。

### 6. 改 `pvz.c` 的注意事项

* **中文注释里的引号用「」**，代码字符串用 ASCII 引号 ——
  混用会让批量替换脚本出错（我因此弄坏过脚本）
* 新增诊断输出**要另起一行**，别插在已有行中间（会把解析脚本拆散）
* 编译必须零警告
* 文件很大（1 万行），改前先 `cp pvz.c pvz.c.bak-<时间>` 备份

### 7. 验证要走"双轨"

* **状态 dump**：断言具体数值（可靠、可自动化）
* **截图目视**：`_dump.exe` 会输出 BMP，转 PNG 后用 Read 工具看
  （很多问题只有肉眼能发现 —— 例如"所有关卡的通关波数都被截断成 20"
   就是靠看截图发现的，状态 dump 显示不出"看起来不对"）

**两个都要做。** 只看 dump 会漏视觉问题，只看截图会漏数值问题。

### 素材生成管线的坑（补素材时会用到）

* `mmx` 在 Windows 上是 `.cmd`，Python `subprocess` 靠 PATH 找不到，
  必须 `["cmd", "/c", r"C:\nvm4w\nodejs\mmx.cmd", ...]`
* mmx **没有音乐生成**（只有 text/speech/image/video/search/vision），
  音乐是 `_gen_music.py` 用 numpy 纯合成 + ffmpeg 转码的
* AI 出图会在**角色脚下画深绿色椭圆投影**，按色距抠图抠不掉 ——
  必须用「绿色主导 + 边界洪水填充」（见 `_install_art.py` 的 `chroma_key`）
* PIL 存 BMP 会丢 alpha（落成 24 位）→ 必须手写 BGRA；
  PIL 读 BMP 也忽略 alpha → 验证要字节级读
